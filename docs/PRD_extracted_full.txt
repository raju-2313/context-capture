Executive Summary People meet useful information constantly while browsing: an explanation, a screenshot-worthy chart, a code snippet, a question that pops up, an idea. Capturing it today means leaving the page, opening another app, and losing track of where it came from. The result is scattered notes with no context. This product is a Chrome-first browser extension that makes capture a one-gesture action and automatically keeps the context of every capture : which page, which tab session, which selection, when, and what the user was thinking. Captures live inside independent per-tab Browser Contexts , can be grouped across tabs into Projects , are findable through search and filters, and can be exported at any time. Product principle: Capture anything. Preserve its context. Connect it. Find it. Use it. Two modes Mode Account Storage Purpose Local Mode (default) None On the device only Fully useful from install. Proves the core value. Signed-in Mode Required to enable Local plus cloud sync Unified library, projects across devices, later AI. Strategic stance The MVP (Phase 1) proves one thing: capturing anything and finding it again is genuinely useful, with zero sign-up. It contains no cloud, no AI and no projects. The data model is designed in Phase 0/1 so that projects, sync and AI arrive later without a rewrite . Stable IDs, many-to-many memberships and a change journal exist from day one, even though only the local parts are used. The differentiation (per-tab contexts plus cross-tab projects plus local-first) is a hypothesis , not a proven advantage. Section 23 and 24 treat it that way. 2. Product Vision and Problem Statement 2.1 Problem Information discovered while browsing is not captured, or is captured in a different tool than the one where it will later be needed. Switching apps breaks flow, so people either skip capture or do it later and forget. Captured items lose their origin (which page, which research thread, which question led to it). Screenshots, links, quotes and thoughts are stored in different places and cannot be searched together. Many existing clippers require an account up front, which is a barrier for casual and privacy-sensitive users. 2.2 Vision A browser-first personal knowledge workspace where capture costs about one keystroke, context is attached automatically, and everything is retrievable later from one place the user owns. 2.3 Value proposition (to be validated) For a researcher or learner who browses with many tabs open: each tab keeps its own capture space, and later the captures from several tabs can be pulled together into one project. For a privacy-conscious user: works with no account, stores locally, never uploads browsing activity, exports everything. 3. Goals and Non-Goals 3.1 Goals ID Goal Phase G1 Capture text, screenshots, links, notes and questions in two interactions or fewer from a page. 1 G2 Every capture carries its source context automatically. 1 G3 Each browser tab has an independent, persistent context that survives tab close and browser restart. 1 G4 Works fully without an account; local-first. 1 G5 Users can retrieve captures through search and filters. 1 (basic), 3 (advanced) G6 Users can export their data (Markdown, PDF, JSON backup) for free. 1 G7 Signed-in users get a unified library, sync and cross-context projects. 2 G8 Smarter retrieval: OCR, related captures, semantic search. 3 G9 Grounded AI answers that cite the user&apos;s own captures. 4 G10 Integrations with note apps where technically feasible. 5 3.2 Non-Goals Not a full note-taking app with rich page layouts, databases or collaboration. Not a browsing-history manager. The product does not record pages the user did not choose to capture. Not a web archiver guaranteeing pixel-perfect page copies (reference saving and readable-text extraction are distinct; full page copies are out of the MVP). Not a replacement for Notion, Obsidian or Apple Notes. Export and later integration are the bridge. No mandatory sign-up, no mandatory AI, no ad-based model. No team or shared workspaces in the initial roadmap [Open] . No Firefox or Safari support at launch [Recommendation] . 4. They must not be blended in UI copy, code or documentation. Term Definition Identity Lifetime Browser Context (short: Context ) The space of captures made while working in one browser tab session. context_id (UUID, product-owned) Persists until the user deletes it. Not tied to the live tab. Tab A live browser tab. Chrome tabId (temporary, session-scoped) Ends when the tab closes or the browser restarts. Capture One saved item: screenshot, selection, link, question, note, code snippet (later: voice). capture_id (UUID) Until deleted. Belongs to exactly one origin Context (or none, see 9.4). Attachment A binary file belonging to a capture (screenshot image, later audio). attachment_id (UUID), content hash Owned by the capture, shared by reference. Project A user-created collection that references captures from any number of Contexts. Has its own description and ordering. project_id (UUID) Until deleted. Deleting a project never deletes captures. Project Membership The link between a capture and a project, with ordering and an optional project-specific note. (project_id, capture_id) Until removed. Library ( All Captures ) The unified view of every capture regardless of context or project. n/a Always available. Account An optional sign-in identity enabling sync. user_id Until account deletion. Workspace The signed-in view combining Library, Projects, Contexts, Search. In Local Mode the same UI exists, scoped to local data. n/a n/a Archive State of a Context whose tab is closed and which is not currently bound to a live tab. status = archived Recoverable. Rules that follow from the terms A Context is not a tab. A tab is only the current binding of a Context. A Project is not a folder. It is a curated, ordered, annotated set of references with its own purpose (description, later custom instructions and AI scope). A Capture has one origin Context but can belong to many Projects. Adding to a Project never moves or copies the capture or its attachments. The Library is a view, not a place. It shows everything; it owns nothing. 6. Product Experience and User Flows 6.1 Experience summary Capture surfaces: keyboard shortcut, right-click context menu, toolbar popup, side panel quick-add. Review surface: side panel with three areas: This Tab , All , Projects (Projects appears in Phase 2), plus Search. Principle: capture first, organise later. Required user input for a capture is zero; optional note, tags and project are one step away. 6.2 Core flows (summary; acceptance scenarios in Section 20) Flow A: First run User installs. A one-screen welcome opens in the side panel: what is stored where (&quot;on this device only&quot;), shortcut keys, how to capture. No sign-in prompt. A neutral &quot;Sign in later to sync&quot; link appears only in settings (Phase 2). Flow B: Capture selected text User selects text on a page. User presses the capture shortcut or uses the right-click item. Capture is saved to this tab&apos;s Context with URL, title, favicon, timestamp and selection text. A toast confirms with Add note , Tag , Undo . Optional: user adds a note in the toast or side panel. No modal blocks the page. Flow C: Screenshot User presses the screenshot shortcut or chooses it in the popup. Phase 1 captures the visible viewport (region capture is P1, see 8.3). Image is stored locally and appears in This Tab immediately. Flow D: Thought or question User opens quick-add (shortcut), types text, chooses Note or Question , presses Enter. Capture is bound to the current tab&apos;s Context with the page&apos;s URL and title attached automatically. Flow E: Switch contexts User changes tab. The side panel&apos;s This Tab view switches to that tab&apos;s Context automatically. Contexts list (under All) lets the user open any Context, including archived ones. Flow F: Close and recover User closes a tab. Its Context becomes Archived , not deleted. User opens Contexts &gt; Archived , sees the Context with name, last URL and capture count, and can open it, rename it, merge it, or bind it to the current tab. Flow G (Phase 2): Account creation and migration , Flow H (Phase 2): Project creation and adding captures . Detailed in Sections 9 and 20. 7. Tab Context and Project Management Specification 9.1 Context identity model Problem: Chrome&apos;s tabId is unique only within a browser session and is not stable across restarts. [Verified] : tab IDs are session-scoped. Therefore: context_id (UUID) is the permanent identity. A binding record maps a live tabId (plus windowId ) to a context_id for the current browser session. Bindings live in session-scoped storage and are rebuilt on startup. Context { context_id, title, status: active | archived, created_at, last_active_at, first_url, last_url, origin_device_id } Binding (session only) { tab_id, window_id, context_id, bound_at } 9.2 Lifecycle Event Behaviour First capture in an unbound tab Create Context ( active ), bind to the tab. Navigation within the tab Context stays bound. last_url updated. Navigation does not create a new Context [Recommendation] . Captures keep their own URL. New tab opened via link from a bound tab New tab gets no Context until the user captures. Optional setting: &quot;Start from parent context&quot; [Open] . Tab closed Binding removed. Context becomes archived . Nothing is deleted. Browser closed or crashes On next start, all contexts are archived until re-bound. Cleanup runs on startup because close events may not fire. Session restore (tabs reopened) Attempt rebinding using matching rules below. User opens an archived Context Can view only , or bind to current tab . Tab discarded or suspended by the browser Tab ID stays the same; binding unchanged. Tab dragged between windows Tab ID stays; update window_id . Extension update or service worker restart Bindings rebuilt from session storage plus a reconciliation scan of open tabs. Rebinding match rules [Recommendation, validate with spike] Only consider archived contexts whose last_url matches the restored tab&apos;s URL exactly (ignoring fragment). If exactly one archived context matches and it was last active in the most recent session, auto-bind and show a dismissible notice: &quot;Restored your context &apos;X&apos;. Not right? Unlink.&quot; If several match, do not auto-bind. Show a chooser the next time the user captures or opens the panel. If none match, behave as a new tab. Optional later signal: Chrome&apos;s session APIs may help correlate restored tabs. [Open] : evaluate during the spike whether any restore signal is reliable enough to use. 9.3 Context management actions Rename, merge, split (P2), archive/unarchive, delete (soft delete with undo and 30-day purge), export. 9.4 Capture ownership A capture has one context_id (its origin) that never changes automatically. Merging contexts is an explicit user action and rewrites context_id while recording the move in the change journal. A capture in the Unfiled context can be moved into any context. 9.5 Projects (Phase 2) A Project is a curated set, not a folder. It has: Property Phase Name, description (purpose) 2 Ordered list of memberships (manual order, sections) 2 Per-membership note (why this item matters in this project) 2 Project-level search and filters 2 Project export (Markdown, PDF, JSON) 2 Project status (active, archived) 2 Custom instructions for AI 4 AI Q&amp;A scoped to project 4 Rules Adding a capture to a project creates a membership , not a copy. Attachments are never duplicated. A capture can be in many projects. Removing it from one project affects only that membership. Deleting a capture warns about project memberships and removes them with it. Deleting a project removes its memberships only. Captures with no membership remain fully visible in the Library (shown as Unassigned filter). Adding to a project from the capture UI is one step (choose or create project, in the same toast or card menu). A bulk-select mode adds many captures at once. Project membership for captures in archived contexts works normally. Example (EV Research): four contexts (Tesla review, BYD review, battery research, personal questions) contribute eleven captures to one project. Each capture still opens in its original context, and the project shows each item with its source context chip. Search and Retrieval Specification 10.1 Principles Reliable non-AI retrieval ships first. AI is an enhancement layered on a working index. Search runs locally in Local Mode; in Signed-in Mode, local search still works offline, and cloud search is additive. Every result shows enough context (type, snippet, source domain, context chip, date) to recognise it without opening. 10.2 Phase plan Capability Phase Approach Notes Keyword full-text over note text, selection text, titles, URLs, tags 1 Local inverted index (library chosen in spike, for example a small in-browser FTS library, or IndexedDB-backed index) [Recommendation] Do not rely on naive substring scans beyond a few thousand records Filters: type, domain, context, tag, date, project 1 (project in 2) Indexed fields Combinable Sort: newest, oldest, by domain 1 n/a n/a Open source page / focus existing tab 1 tabs APIs n/a OCR of screenshots 3 Bundled WASM OCR run locally in an offscreen/extension page, queued in background Processing status shown; user can disable; language packs add size [Assumption] accuracy acceptable for UI text, weaker on charts and low-contrast images Duplicate detection 3 (URL warning in 1) URL normalisation, text hash, image perceptual hash Never auto-delete Related captures 3 Shared tags, domain, term overlap, later embeddings Must explain why items are related Semantic search 3 or 4 Embeddings. Local small model vs cloud service is [Open] Cloud use needs consent (PRV-003) Natural-language Q&amp;A 4 Retrieval-augmented generation See 10.3 10.3 AI answers: grounding rules (Phase 4) Evidence-first: retrieve relevant captures, pass them as clearly delimited data , and require the answer to cite capture IDs. Separate evidence from assumption: answers have two labelled parts when needed: From your captures and Not found in your captures / general knowledge . Prompt-injection defence: captured webpage text is untrusted. It is always wrapped as quoted data, never merged into system instructions, and the model is told to ignore any instructions found inside it. Outputs that attempt to trigger actions (links to fetch, tool calls) from captured text are not executed. Tool use by the assistant, if any, requires user confirmation. It must hold no required state in memory . All state lives in IndexedDB or storage.session . All event listeners are registered synchronously at top level. Long jobs (export, OCR, PDF) run in an offscreen document or an extension page, report progress by message, and checkpoint in the DB. Cross-context messaging uses a typed protocol with request IDs and timeouts. 14.4 Permissions philosophy Prefer activeTab (temporary access after a user gesture, no install warning [Verified] ), scripting , contextMenus , storage , sidePanel [Verified requirement] , unlimitedStorage , downloads , offscreen . Avoid &lt;all_urls&gt; host permissions, history , webRequest and debugger . Decision needed on tabs [Open, high impact]. Title, URL and favicon of the active tab are available through activeTab after a gesture [Verified] . Tracking tab closes needs only tab IDs (no URL), but a cross-tab Contexts list with live URLs, and rebinding after session restore by URL, may need the tabs permission, which shows a broad browsing-data warning at install. Privacy-preserving default: track only tab ID to context ID from events, read the URL only at capture time, and store last_url only when a capture happens. The UI reads only local data. Every mutation writes a change journal entry (entity, operation, timestamp, device ID, version) from Phase 1, even before sync exists, to avoid a retrofit. IDs are client-generated UUIDs (v4, or time-ordered v7), so offline creation never collides. Deletes are tombstones until synced and purged. Attachments are content-addressed (SHA-256) and uploaded separately from metadata. 14.7 Cloud stack (Phase 2) [Open] A managed backend (managed Postgres, object storage, hosted auth) minimises operations for a small team. Selection criteria: row-level isolation, signed and resumable uploads, support for data export and deletion, region choice, cost predictability. Phase 0 produces a short decision record; this PRD does not mandate a vendor. 14.8 Sync engine (Phase 2) Model: push and pull over the change journal with per-entity versions; metadata sync separate from attachment transfer. Conflict policy [Recommendation]: Different fields edited on two devices: field-level merge. Same field edited on both: keep both; show a conflict card with the other version preserved as a conflict copy. No silent overwrite. Edit versus delete: restore the item and notify. Project ordering: merge by order keys; deterministic tie-break, visible to the user. Retries: exponential backoff with jitter; resumable attachment uploads; per-item status so one failure does not block others. Idempotency: the server accepts the same change ID repeatedly. Ordering: server-assigned sequence numbers rather than device clocks. 14.9 Local-to-cloud migration (Phase 2) On first sign-in, show counts and size of local data and options: Sync everything , Choose contexts , Stay local . Local data is never deleted or modified by migration. Cloud copies are created alongside. Migration is a resumable job with a persisted checkpoint: metadata first in batches, then attachments by hash. Duplicate detection against existing cloud data (for an account that already has data from another device): match by capture ID, then by attachment hash plus source URL plus a timestamp window. Matches are linked, not duplicated; uncertain matches ask the user. Interrupted upload: resumes from the last checkpoint on next start; partial attachments are verified by hash and re-sent if incomplete; progress and a Retry button are visible. Individual item failures are listed with reasons; the rest completes. Final verification compares counts and hashes; mismatches are reported, not hidden. A pre-migration local backup file is offered automatically. 15.
